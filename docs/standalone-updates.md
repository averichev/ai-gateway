# Подписанные обновления AI Gateway

Глобальный владелец управляет выпусками на странице **Конфигурация → Обновления**. Без `GATEWAY_UPDATE_SOURCE` страница показывает установленную версию. Проверка обращается к издателю только по команде владельца.

| Развёртывание | Режим | Как устанавливается выпуск |
| --- | --- | --- |
| Docker, macOS или установка под управлением пакетного менеджера | `external`, по умолчанию | Админка проверяет подпись выпуска standalone-бинарника. В Docker оператор отдельно выбирает образ через `agctl image set` и устанавливает его через `agctl apply`. |
| Отдельная Linux-служба под systemd | `supervisor` | Исходный процесс сохраняет PID и запускает рабочую копию из приватного каталога. |
| Linux-процесс с исполняемым файлом, которым владеет пользователь службы | `standalone` | Updater заменяет файл и запускает процесс с новым PID. Бинарник и каталог обновлений должны находиться на одной файловой системе. |

## Подключение канала

Официальный канал задан в `.env.example` и в окружении, которое создаёт `agctl init`. Чтобы подключить канал на существующей установке, задайте переменную в окружении службы и перезапустите её. Для развёртывания через `agctl` добавьте строку в рабочий `.env` и выполните `agctl apply`. UUID продукта и публичный ключ уже встроены в AI Gateway.

```dotenv
GATEWAY_UPDATE_SOURCE=https://app.releases.veruna.systems/ai-gateway/manifest.json
```

При проверке шлюз делает один GET к манифесту и ищет более новую стабильную версию для своей платформы. Публикуйте бинарники на том же HTTPS-origin, что и манифест (схема, хост и порт), включая адрес после перенаправлений. Лимит одного бинарника — 256 МиБ. Для локальной проверки допустим HTTP на loopback IP.

Если уже используется абсолютный путь к `update-source.json`, он продолжит работать со своим ключом и правилами загрузки. Для перехода сначала опубликуйте манифест с подписями AI Gateway, затем замените путь на URL.

## Подпись выпуска

Постоянный UUID AI Gateway — `cf9f6111-304c-40e4-8c78-6c84e600dd9e`. Для регистрации у издателя используйте этот UUID и публичный ключ приложения. [Публичный Ed25519 JWK](../src/updates/public-key.json)

Приватный ключ хранится на машине подписания. Скрипт читает его из `${XDG_CONFIG_HOME:-$HOME/.config}/ai-gateway/release-signing/ed25519.pem` или по пути в `GATEWAY_UPDATE_SIGNING_KEY`.

Для следующего выпуска увеличьте стабильную версию в `Cargo.toml`, обновите `Cargo.lock` и выполните `make standalone-release`. На Linux нужной архитектуры получите BuildInfo из окончательного бинарника. Передайте этот же файл и его BuildInfo на машину подписания.

```sh
target/release/ai-gateway --standalone-updater-build-info > build-info.json
node scripts/sign-update.mjs target/release/ai-gateway build-info.json > signed_metadata.jws
```

Скрипт подписывает UUID, версию, ОС, архитектуру, размер и SHA-256 файла. Поместите строку из `signed_metadata.jws` в поле `signed_metadata` соответствующего бинарника в манифесте схемы 2. Для каждой архитектуры нужна собственная подпись. Сначала разместите бинарник, затем опубликуйте манифест. [Контракт издателя](https://github.com/averichev/standalone-updater/blob/b43612dd7528185877654428520d57098462f8e7/docs/integration.md)

```json
{
  "schema_version": 2,
  "releases": [{
    "version": "0.1.1",
    "artifacts": [{
      "purpose": "executable",
      "target": "linux-aarch64",
      "download_url": "<полный HTTPS-адрес бинарника на том же хосте и порту, что и манифест>",
      "signed_metadata": "<строка из signed_metadata.jws>"
    }]
  }]
}
```

## Отдельная Linux-служба

На Linux с Rust 1.91+ и Node.js 22.12+ соберите первый бинарник со встроенной админкой и проверьте его идентификаторы. Путь в примере соответствует стандартному каталогу Cargo.

```bash
make standalone-release
target/release/ai-gateway --standalone-updater-build-info
```

Установите бинарник и системные корневые сертификаты (в Debian и Ubuntu это пакет `ca-certificates`). Сохраните рабочие `DATABASE_URL` и `GATEWAY_MASTER_KEY` в окружении службы. Задайте режим и приватный каталог, принадлежащий пользователю службы с правами `0700`. Путь должен допускать запуск файлов и проходить через каталоги без симлинков и без права записи для посторонних.

```dotenv
GATEWAY_UPDATE_MODE=supervisor
GATEWAY_UPDATE_DIR=/var/lib/ai-gateway/updater
```

Запускайте службу с фиксированным `APP_PORT` и локальным либо wildcard-адресом `APP_HOST`. При установке сервер завершает HTTP-запросы, закрывает пул PostgreSQL и подтверждает остановку. Updater проверяет по loopback `GET /ready`, версию и идентификатор нового процесса. Маршрут читает таблицу `users`. Обычный `/health` остаётся проверкой HTTP.

Бинарник со встроенной админкой обновляет сервер и интерфейс вместе. В обычной Cargo-сборке файлы `ADMIN_DIST_DIR` поставляются отдельно. Updater требует совпадения полного Rust target и отпечатка встроенных SQLx-миграций, формата хранения секретов и способа доставки админки. Выпуск с изменением этих условий устанавливайте вручную с резервной копией БД. Автоматический откат восстанавливает исполняемый файл. Данные PostgreSQL сохраняются.

## Установка и восстановление

1. Нажмите **Проверить выпуск**, затем **Подготовить**. Шлюз продолжает обслуживать запросы во время загрузки и проверки файла.
2. После подготовки выберите **Установить** и подтвердите показанную версию. Подготовку также можно отменить. Для установки подготовленного файла сеть издателя уже не требуется.
3. Дождитесь итогового состояния и проверьте установленную версию. После успешного обновления перезагрузите интерфейс.

При сбое запуска или готовности библиотека пытается вернуть предыдущую версию. Если статус требует ручного восстановления в режиме `standalone`, остановите процессы службы и вызовите установленный бинарник с `--standalone-updater-recover` от пользователя службы, с исходным окружением и рабочим каталогом. Затем запустите службу и проверьте её готовность. В режиме `supervisor` восстановление прерванного переключения выполняется при следующем запуске исходного бинарника.

### HTTP API владельца

Все операции требуют действующей сессии глобального владельца в `Authorization: Bearer`. Статус доступен по `GET /api/admin/updates`. В нём есть текущая версия, режим установки, её доступность и `status` с этапом, идентификатором операции и результатом.

| POST-маршрут под `/api/admin/updates` | JSON | Результат |
| --- | --- | --- |
| `/check` | без тела | `202`, опрашивайте статус до завершения проверки |
| `/prepare` | `{"check_id":"…","version":"…"}` | `202`, опрашивайте до `prepared` |
| `/install` | `{"operation_id":"…"}` | `202`, опрашивайте после перезапуска до `completed`, `rolled_back` или `failed` |
| `/cancel` | `{"operation_id":"…"}` | `200`, подготовка отменена |

Для `check_id` используйте `status.operation_id` проверки выбранного выпуска. При `409` перечитайте статус. Установка разрешена только для проверенного и подготовленного файла.
